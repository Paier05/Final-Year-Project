## 3. Environment interface

Verified by introspecting the installed `arc-agi` 0.9.9 package rather than
guessing method names, as the issue requires.

```python
arcade = arc_agi.Arcade(arc_api_key="", arc_base_url="https://three.arcprize.org")
environments = arcade.get_environments()        # -> list[EnvironmentInfo]
env   = arcade.make(game_id, seed=seed)         # -> EnvironmentWrapper
frame = env.reset()                             # -> FrameDataRaw
frame = env.step(action, data=..., reasoning=...)
```

`FrameDataRaw` carries `game_id`, `state`, `levels_completed`, `win_levels`,
`action_input`, `guid`, `full_reset`, `available_actions: list[int]`, and a
`frame` property returning `list[ndarray]`.

Four facts that shaped the harness:

1. **`GameAction(6)` raises.** Members are keyed internally by `(value, kind)`
   tuples, so the library's own `GameAction.from_id(6)` is the correct accessor.
   This was found by the offline self-test, not in production.
2. **`available_actions` is authoritative, `tags` is not.** `ft09` reports
   `available_actions=[6]` (click-only) while its `tags` list is empty. The
   harness keys off `available_actions` every step.
3. **Click coordinates are frame pixel coordinates.** `ACTION6` takes
   `data={"x":…, "y":…}` in screen coordinates; `camera._calculate_scale_and_offset()`
   returns `(2, 0, 0)`, so the 32×32 world renders at 2× into the 64×64 frame and
   screen coords map 1:1 onto frame indices. The agent is therefore told
   `x, y ∈ 0..63`, matching exactly what it sees.
4. **Environments run locally.** `arcade.make()` downloads the game and executes
   it via `LocalEnvironmentWrapper`. Stepping costs no ARC API calls and is fast,
   so essentially the entire cost of this experiment is the model endpoint.
   (Flagged in the work log: this does mean executing third-party downloaded
   code, which is the official toolkit's documented behaviour.)

### 4.1 Perception (plain code, no LLM)

Per the issue, perception is deliberately non-neural. Each frame yields grid
size, a colour-count summary, and the list of non-background 4-connected
components sorted largest-first (so truncation at `max_objects=40` keeps the
salient ones). Background is the most frequent colour.

The frame diff is kept **structured**, not just rendered as text, because
Phase 3 mines action-effect rules directly out of those diff records. Each diff
carries the changed-cell list, a colour-transition histogram, and the bounding
box of the change.

> **Known limitation, stated up front.** Object `id`s are recomputed every step
> by size order, so `id=3` on one step need not be the same object on the next.
> The system prompt tells the model this explicitly and instructs it to identify
> objects by colour and position. Stable object tracking is listed in
> [next steps](#10-next-steps).

**Optional vision channel.** `observation.send_image` renders the grid to a PNG
and attaches it as a second content part, since Qwen3.8-27B is a VLM. The issue
asks for both configurations if budget allows; this is a config flag, default
`false`.

### 4.2 Memory and scratchpad rules

The model's only memory beyond the last `N=10` (action, effect) pairs is a
free-text scratchpad it rewrites every step by returning a `scratchpad` field.
It is capped at 2000 characters. Omitting the field keeps the previous notes
unchanged. The system prompt tells it to record established dynamics and goal
hypotheses rather than a narration of events.

### 4.3 Action schema

```json
{"thought": "...", "action": "ACTION1", "args": {}, "scratchpad": "..."}
```

`action` ∈ `RESET, ACTION1..ACTION7` (plus `CALL` in Round 1). `args` must be
`{}` for everything except `ACTION6`, which requires `{"x": int, "y": int}` with
both in `0..63`.

Parsing is strict about the *decision* and lenient about *formatting*: a
markdown fence, a `<think>` block, surrounding prose, `col`/`row` aliases, a
2-element `coord` list, numeric strings and bare action ids are all accepted,
because those are presentation slips rather than wrong choices. Anything else —
unknown action, out-of-range coordinate, missing click args, no JSON at all — is
a **counted parse failure**: retry once with the error fed back, then fall back
to a random *non-RESET* available action so the fallback cannot destroy
progress. Parse-failure rate is reported per episode.

### 4.4 Budgets and termination

| Budget | Default |
|---|---|
| Max actions on Level 1 | 200 |
| Wall clock per episode | 1200 s |
| Max resets per episode | 10 |
| Max tokens per episode | 600 000 |

An episode ends on: `levels_completed >= 1` (**solved**), engine `WIN`
(**solved**), or any budget. On `GAME_OVER` the harness auto-resets and counts
the reset, continuing until the reset cap — this is the issue's "reset allowed,
count resets".

### 4.5 The exact system prompt

Verbatim, as sent (also written to `docs/system_prompt.txt` by the harness):

```text
You are playing an ARC-AGI-3 video game through a text harness. You see a
coloured grid and choose one action per turn. Nobody tells you the rules of the
game: you must work them out by acting and watching what changes.

YOUR TASK: complete LEVEL 1 of this game in as few actions as possible.

THE GRID
- The observation is a 2D grid of colour indices. Row 0 is the top, column 0 is
  the left. Coordinates are written (row, col).
- Colour legend: 0=black, 1=blue, 2=red, 3=green, 4=yellow, 5=grey, 6=magenta,
  7=orange, 8=cyan, 9=maroon, 10=pink, 11=lime, 12=teal, 13=brown, 14=navy,
  15=white
- Perception is done for you by plain code: you get the grid size, a colour
  histogram, and a list of connected-component objects with their colour,
  bounding box, size and centroid. Object ids are recomputed every step by
  size order, so id=3 on one step is NOT necessarily the same thing as id=3 on
  the next step. Identify objects by colour and position, not by id alone.

ACTIONS
- ACTION1 .. ACTION5 are simple actions with no arguments. Their meaning is
  game-specific and unknown to you. In many games some of them are directional.
- ACTION6 is a click. It REQUIRES arguments: {"x": <col>, "y": <row>} where x
  is the column and y is the row, both integers in 0..63. Note the
  order: x is horizontal (column), y is vertical (row).
- ACTION7 is another simple action with no arguments.
- RESET restarts the level. It is allowed and sometimes necessary after a
  game-over, but every reset is counted against you, so do not use it to
  explore.
- Only the actions listed as AVAILABLE in the observation will have any effect.
  Choosing an unavailable action wastes a turn.

HOW TO PLAY WELL
- Early on, your job is to learn the dynamics: try each available action and
  read the diff carefully to see what it did.
- Once you know what an action does, stop re-testing it and start using it to
  make progress.
- If an action produces no change at all, that is information: the action may be
  blocked, irrelevant, or need different arguments.
- If the same thing keeps not working, change your approach instead of repeating
  it. Repeating a no-op action is the single most common way to waste the budget.
- Keep notes in the scratchpad. It is the only memory that survives beyond the
  last 10 steps, so record what you have established about the
  dynamics and the goal, not a narration of events.

OUTPUT FORMAT
Reply with a single JSON object and nothing else. No prose before or after, no
markdown code fence. The schema is:

{"thought": "<brief reasoning, one or two sentences>",
 "action": "<one of RESET, ACTION1, ACTION2, ACTION3, ACTION4, ACTION5, ACTION6, ACTION7>",
 "args": {},
 "scratchpad": "<your updated notes, under 2000 characters>"}

"args" must be {} for every action except ACTION6, where it must be
{"x": <int>, "y": <int>}. If "scratchpad" is omitted your previous notes are
kept unchanged.
```

In Round 1 the skill library block and the module-call instructions are appended
to this prompt; nothing else changes.

## 6. The learning process

Mining runs over dev-game Round 0 trajectories only. Each candidate skill is
validated by replaying it against the logged data and is dropped if it fails.
Admission thresholds: support ≥ 8 (≥ 3 for macros and goals) and precision
≥ 0.60.

### 6.1 Action-effect rules

Two forms, strongest first.

**Translation rules.** An object moving by `(dr, dc)` appears in the diff as *k*
cells going colour→background and *k* cells going background→colour, with the
two centroids offset by exactly the move. Detecting that balanced pattern yields
rules of the form *"ACTION1 moves the moving object up by 1 cell"* — which is
precisely the example the issue gives.

**Signature rules.** Where no clean translation exists, the step is reduced to a
coarse signature (change magnitude bucket + dominant colour transition) and the
dominant signature per `(game, action)` becomes the rule — including the useful
negative case *"ACTION2 usually does nothing at all"*.

**Precision is measured on held-out data.** Rules are fitted on all but the
last seed and scored on that held-out seed, so a reported precision is not the
fit statistic. Each stored skill records `support`, `precision`, the holdout
seed, and `n_checked`/`n_hits`.

### 6.2 Macro-actions

Length-2 and length-3 action subsequences, counted against how often the window
ended on a `levels_completed` increase or a `WIN`. Stored with both the raw
occurrence count and the hit rate, so a macro that merely occurs often does not
look good.

### 6.3 Code modules

Four deterministic helpers in `learning/modules.py`, callable as tools in
Round 1:

| Module | What it does |
|---|---|
| `player_detector` | ranks which object is the agent-controlled sprite (small, uniquely coloured) |
| `obstacle_map` | classifies each colour wall-like vs item-like; reports border-touching colours |
| `bfs_to_target` | shortest 4-connected path length between two cells with given colours impassable, or UNREACHABLE |
| `grid_region` | prints raw colour indices for a rectangle, to pin down an exact click coordinate |

A module is admitted only if it ran with **zero exceptions** and returned a
useful (non-degenerate) answer on most grids reconstructed from logged dev
frames. Calling one costs a turn of thinking but **no game action**; the system
prompt warns against calling them in a loop. Unknown or unvalidated module names
are refused by `SkillLibrary.run_module` rather than executed.

### 6.4 Goal hypotheses

For each dev game, the action that triggered each `levels_completed` increase
and the board state at that moment, aggregated into *"the level likely completes
on ACTION_k, with N objects on screen"*.

### 6.5 Skill storage

One JSON file per skill in `skills/`, plus `skills/index.json` listing every
kept skill with name, kind, description, source games, support, precision,
usage hint, and file — and every **dropped** candidate with its reason, so the
filtering is auditable.

## 7. Results

**Not available.** Round 0 and Round 1 have not been run, because the model
credential is rejected (§1). No numbers are presented here rather than

Once a working key is in `.env` as `ARC_MODEL_API_KEY`, the whole experiment is:


### 7.1 What it will cost, measured rather than guessed

A real `ls20` step is a 2918-character system prompt plus a 3341-character user
message — about **1.6k input tokens per step**. At the 200-action budget that is
roughly **320k input tokens per episode**, and the full specified sweep is
25 games × 3 seeds × 2 rounds = **150 episodes**, so the worst case is on the
order of **50M input + 10M output tokens**. Episodes that solve early cost far
less. `limits.global_token_cap` is set to 80M and aborts the sweep if exceeded.

**Wall clock is the bigger constraint.** 150 episodes × up to 200 model calls is
up to 30 000 calls; at a typical few seconds per call that is on the order of
**one to three days** of sequential running. The 1200 s per-episode wall-clock
cap means many episodes will stop on time rather than on actions. Practical
options, in order of preference: shard across processes with `--games`, set
`model.thinking: "off"`, or reduce `run.seeds` / `budget.max_actions`. **Reducing
scope is the user's call, so the defaults ship at the issue's full
specification.**

## 8. Verification performed

No test suite exists for this code, so verification was done against the real
environment with a deterministic offline policy.

- **`run.py --stub`** replaces the model with a random-but-legal policy that
  parses the *real* prompt text and drives the *real* ARC environment. Two games
  × 200 actions ran end to end. It writes to a separate episodes file and its
  numbers are explicitly **not results**.
- This caught a genuine bug before any spend: `GameAction(6)` raises because
  members are keyed by `(value, kind)`; `GameAction.from_id` is correct.
- **Trajectory records** were checked to contain every field the issue lists,
  and frames were confirmed saved as a `(201, 64, 64)` int16 array — replayable.
- **The GAME_OVER path executed for real** on `vc33` (4 auto-resets, counted).
- **Action parsing** was unit-exercised over 14 cases: fenced JSON, `<think>`
  wrappers, surrounding prose, `col`/`row` and `coord` aliases, numeric strings,
  and seven malformed inputs that must fail — all behaved as specified.
- **The miner** ran on self-test trajectories and produced 6 validated skills
  with support and held-out precision, writing `skills/index.json` correctly.
- **Round 1 injection** was verified: library loads, prompt block and tools block
  render, modules execute, and an unknown module name is refused.
- **All six figures** generated and were visually inspected for legibility.
- **The abort path was verified against the live endpoint:** `--stage preflight`
  correctly stopped with an actionable message on the 401.
- The categorical palette was checked with the colour validator
  (3 slots, all-pairs, light mode): lightness band, chroma, CVD separation and
  normal-vision floor all PASS; one slot carries a contrast WARN, answered by
  direct value labels and by `summary.csv` as the table view.

Self-test artifacts were deleted before committing so that no stub-derived
figure or skill file could be mistaken for a result.

## 9. Per-game notes and failure modes

**Not available** — these require Round 0 trajectories. The analysis to produce
them is built: `frame_diff` records, `model_thought`, and the scratchpad are
logged for every step, which is what the per-game "what it figured out / where
it got stuck" breakdown will be written from.

The failure-mode taxonomy the report will use (perception / dynamics / goal /
planning) maps onto signals already logged:

| Failure mode | Signal in the logs |
|---|---|
| Perception | acts on objects that the object list does not support |
| Dynamics | repeats an action whose logged diff is consistently `no change` |
| Goal | learns the dynamics (high-precision action-effect rules) but never raises `levels_completed` |
| Planning | correct dynamics and correct target, but exhausts the action budget |
| Format | non-zero `parse_failures` / `fallback_actions` |

## 10. Next steps

1. **Unblock the credential.** Everything else is ready; this is the only thing
   standing between the current state and results.
2. **Decide the cost/scope trade-off** before launching (§7.1): full spec is
   ~1–3 days sequential. Sharding with `--games` is the cheapest fix.
3. **Stable object tracking.** Recomputed per-step object ids are the clearest
   known weakness of the Round 0 perception. Matching components across frames
   by colour and proximity would let the model refer to a thing over time, and
   would make translation-based action-effect rules much easier to mine.
4. **Run the image-channel configuration.** `observation.send_image` is built but
   unexercised; Qwen3.8-27B is a VLM and the text rendering may be the binding
   constraint rather than the reasoning.
5. **Tighten the macro miner.** Mining only length-2/3 windows that end on
   progress is crude; with real trajectories, mining from the *successful suffix*
   of solved episodes would likely yield stronger macros.
